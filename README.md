# F2F Bank — E2E Tests

Автоматизированные end-to-end тесты для учебного веб-приложения **F2F Bank**, реализованные на **TypeScript + Playwright**.

Приложение позволяет пользователям регистрироваться, авторизовываться, просматривать профиль, пополнять баланс, просматривать историю транзакций и выполнять переводы по номеру телефона.

## Запуск приложения

Клонировать репозиторий:

```bash
git clone https://github.com/Saqquella/f2f-bank-tests.git
cd f2f-bank-tests
```

Запустить приложение:

```bash
docker compose up -d --build
```

После успешного запуска приложение доступно по адресу:

```text
http://localhost
```

Остановить контейнеры:

```bash
docker compose down
```

Остановить контейнеры и удалить данные базы:

```bash
docker compose down -v
```

## Установка зависимостей для тестов

Установить npm-зависимости:

```bash
npm ci
```

Установить Chromium для Playwright:

```bash
npx playwright install chromium
```

## Структура тестов

```text
tests/
├── auth.spec.ts
├── register.spec.ts
├── profile.spec.ts
├── transactions.spec.ts
├── transfers.spec.ts
└── services/
    ├── authservice.ts
    └── userfactory.ts
```

`AuthService` содержит общие действия регистрации и авторизации и синхронизирует их с соответствующими HTTP-ответами.

`UserFactory` создаёт уникальных пользователей для тестов, которым требуется независимое состояние backend.

Тесты разделены по функциональным модулям приложения.

## Параллельное выполнение

В `playwright.config.ts` включён:

```ts
fullyParallel: true
```

Независимые тесты используют отдельные тестовые данные и могут безопасно выполняться параллельно.

Набор тестов авторизации и профиля использует одного подготовленного пользователя, создаваемого в `beforeAll`. Для этого `describe` используется:

```ts
test.describe.configure({ mode: 'default' });
```

Это локально отключает fully-parallel режим наборов auth и profile и предотвращает конкуренцию нескольких workers за общее backend-состояние. Остальные тесты продолжают выполняться параллельно.

## Подход к тестированию

Основные пользовательские сценарии проверяются через UI Playwright.

Для критичных операций дополнительно проверяются HTTP request/response, когда сетевой результат является существенной частью ожидаемого поведения.

Тестовые пользователи генерируются автоматически. Для независимых сценариев создаются отдельные пользователи, чтобы тесты не зависели от порядка выполнения и могли безопасно запускаться параллельно.

В тестах не используются фиксированные `sleep`/`waitForTimeout` для синхронизации UI. Ожидания строятся на Playwright locators, assertions и сетевых событиях.

## Приоритеты

| Приоритет   | Значение                                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| Критический | Основной пользовательский или финансовый сценарий; нарушение делает ключевую функцию приложения неработоспособной |
| Высокий     | Существенное нарушение бизнес-правил или валидации                                                                |
| Средний     | Важная проверка поведения, UX или граничного случая                                                               |
| Низкий      | Дополнительная проверка навигации, отображения или второстепенного поведения                                      |

## Известные дефекты

В ходе исследовательского тестирования обнаружены дефекты в валидации регистрационных данных, обработке денежных значений, floating-point арифметике, сообщениях валидации и отображении истории транзакций.

Полное описание найденных проблем, шаги воспроизведения, фактический и ожидаемый результат находятся в:

```text
NOTES.md
```

Подтверждённые дефекты, для которых уже подготовлены regression-сценарии, помечаются через `test.fixme()`.

`test.fixme()` не используется для сокрытия flaky или недописанных тестов.
