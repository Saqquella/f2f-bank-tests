# NOTES.md

## Найденные дефекты

### BUG-001 — Регистрация принимает некорректные данные

**Модуль:** Registration  
**Приоритет:** Средний  
**Статус:** Known issue

**Шаги воспроизведения:**
1. Открыть страницу регистрации.
2. Заполнить имя и фамилию строками большой длины и/или спецсимволами.
3. Ввести некорректный либо неполный email, например `a@a`.
4. Ввести пароль из одного символа.
5. Нажать `Register`.

**Фактический результат:**  
Пользователь может быть зарегистрирован при явно слабых или некорректных значениях отдельных полей.

**Ожидаемый результат:**  
Приложение должно валидировать входные данные до создания пользователя: ограничивать разумную длину текстовых полей, проверять формат email и применять минимальные требования к паролю.

**Примечание:**  
Не следует считать наличие спецсимволов само по себе XSS-уязвимостью. Для этого отдельно нужно доказать, что значение выводится без безопасного экранирования.

### BUG-002 — Отсутствует корректная обработка пробельных значений при регистрации

**Модуль:** Registration  
**Приоритет:** Средний  
**Статус:** Known issue / покрыт `test.fixme()`

**Шаги воспроизведения:**
1. Открыть страницу регистрации.
2. Ввести в одно из обязательных текстовых полей значение, состоящее только из пробелов, либо добавить лишние пробелы в начале/конце значения.
3. Заполнить остальные обязательные поля валидными данными.
4. Нажать `Register`.

**Фактический результат:**  
Пробельные значения не всегда отбрасываются или нормализуются перед обработкой.

**Ожидаемый результат:**  
Перед валидацией текстовые значения должны быть нормализованы (`trim`), а поля, которые после этого становятся пустыми, должны считаться невалидными.

### BUG-003 — При сумме перевода `0` отображается некорректное сообщение об ошибке

**Модуль:** Transfers  
**Приоритет:** Средний  
**Статус:** Known issue / покрыт `test.fixme()`

**Шаги воспроизведения:**
1. Авторизоваться.
2. Заполнить корректный номер телефона.
3. Ввести сумму `0`.
4. Заполнить назначение платежа.
5. Нажать `Send`.

**Фактический результат:**  
Перевод блокируется, но приложение отображает сообщение `Please fill in all fields`.

**Ожидаемый результат:**  
Перевод должен быть заблокирован сообщением, явно указывающим причину, например `Amount must be greater than zero`.

**Примечание:**  
Само бизнес-правило «сумма должна быть строго больше нуля» выполняется, но пользователь получает неверное сообщение валидации.

### BUG-004 — Сумма с количеством знаков после запятой больше двух принимается системой

**Модуль:** Transfers / Balance  
**Приоритет:** Высокий  
**Статус:** Known issue

**Шаги воспроизведения:**
1. Авторизоваться.
2. Ввести сумму перевода или пополнения с большим количеством знаков после запятой, например `0.0000000000001`.
3. Подтвердить операцию.

**Фактический результат:**  
Система принимает значение, хотя для денежной суммы не задано ограничение точности. В последующих вычислениях могут появляться артефакты двоичной арифметики с плавающей точкой.

**Ожидаемый результат:**  
Фронтенд и бэкенд должны принимать денежные суммы только в допустимом формате, например не более двух знаков после десятичного разделителя.

### BUG-005 — Баланс отображается с артефактом floating-point arithmetic

**Модуль:** Transactions / Balance  
**Приоритет:** Высокий  
**Статус:** Known issue

**Шаги воспроизведения:**
1. Создать пользователя с балансом `0`.
2. Последовательно пополнить баланс на `0.1`, `0.4` и `0.3`.
3. Проверить итоговый баланс в шапке приложения.

**Фактический результат:**  
Вместо ожидаемого `0.8` отображается значение вида `0.7999999999999999`.

**Ожидаемый результат:**  
Денежный баланс должен отображаться и вычисляться с фиксированной денежной точностью, например `0.80`.

**Вероятная причина:**  
Использование двоичного типа с плавающей точкой для денежных вычислений без нормализации/округления.

**Примечание:**  
Для денежных значений обычно используют целое количество минимальных денежных единиц либо decimal-арифметику, а форматирование выполняют отдельно.

### BUG-006 — Сумма с избыточной точностью может некорректно пройти проверку достаточности баланса

**Модуль:** Transfers  
**Приоритет:** Высокий  
**Статус:** Требует сохранения как отдельный regression case

**Предусловие:**  
Баланс пользователя равен `9.1`.

**Шаги воспроизведения:**
1. Ввести корректный номер телефона.
2. Ввести сумму `9.100000000000000002`.
3. Заполнить назначение платежа.
4. Нажать `Send`.

**Фактический результат:**  
Операция может быть принята системой, несмотря на то, что введённое текстовое значение математически больше отображаемого баланса.

**Ожидаемый результат:**  
Сумма с недопустимой денежной точностью должна быть отклонена до проверки достаточности средств.

**Техническое примечание:**  
Такое значение может быть преобразовано JavaScript/бэкендом к ближайшему представимому IEEE-754 числу и фактически стать равным `9.1`. Поэтому корректнее описывать дефект как отсутствие ограничения денежной точности и небезопасное использование floating-point для денежных значений, а не как подтверждённый способ ухода баланса в минус.

### BUG-007 — В таблице транзакций перепутаны колонки типа и статуса операции

**Модуль:** Transactions  
**Приоритет:** Средний  
**Статус:** Known issue

**Шаги воспроизведения:**
1. Авторизоваться.
2. Выполнить успешное пополнение баланса.
3. Открыть страницу `Transactions`.
4. Сравнить заголовки `Operation Type` / `Operation Status` со значениями строки.

**Фактический результат:**  
Под колонкой `Operation Type` отображается значение статуса (`completed`), а под `Operation Status` — тип операции (`deposit`).

**Ожидаемый результат:**  
Тип операции должен отображаться под `Operation Type`, а статус — под `Operation Status`.

### BUG-008 — Перевод по номеру телефона не выполняется между пользователями

**Модуль:** Transfers  
**Приоритет:** Критический  
**Статус:** Known issue / блокирует полноценный E2E-сценарий

**Шаги воспроизведения:**
1. Авторизоваться как отправитель. Отправитель имеет достаточный баланс.
2. Выполнить перевод на корректно оформленный номер телефона.
3. Проверить баланс отправителя и получателя.

**Фактический результат:**
Средства списываются с баланса отправителя, но получатель по номеру
телефона не определяется и средства ему не зачисляются.

**Ожидаемый результат:**
Система должна определить получателя по номеру телефона, уменьшить баланс
отправителя и увеличить баланс получателя на сумму перевода.

**Примечание:**
Текущая модель пользователя не содержит номера телефона, поэтому полноценный
E2E-сценарий sender → recipient невозможно реализовать до изменения
бизнес-логики приложения.

## Общие замечания по тестам

- Известные дефекты, из-за которых корректный автотест должен падать, помечаются через `test.fixme()` с понятным комментарием.
- `test.fixme()` используется только для подтверждённых дефектов приложения, а не для нестабильных или недописанных тестов.
- Для переводов каждый тест создаёт отдельного пользователя, чтобы тесты не влияли друг на друга и могли безопасно выполняться параллельно.
- Для денежных операций дополнительно проверяется не только UI, но и сетевой результат (`request` / `response`), когда это важно для бизнес-требования.
